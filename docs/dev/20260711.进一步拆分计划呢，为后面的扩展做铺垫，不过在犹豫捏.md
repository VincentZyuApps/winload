# 进一步拆分计划：为后续扩展做铺垫，但先保持谨慎

> 记录时间：2026-07-11
>
> 背景：`main`、`ui`、`i18n` 在 Rust / Python 两边都开始偏长，后续如果继续加功能，维护成本会变高。
>
> 状态：只是拆分计划备忘，不一定立刻做。

## 当前观察

当前较长的文件大致是：

| 语言 | 文件 | 当前职责 |
|---|---|---|
| Python | `python/src/winload/main.py` | CLI、version、debug-info、curses runtime 入口 |
| Python | `python/src/winload/ui.py` | curses UI、header、panel、debug overlay、键盘处理 |
| Python | `python/src/winload/i18n.py` | 所有语言文案 + `t/set_lang/get_lang` |
| Rust | `rust/src/main.rs` | CLI、App、run loop、version、debug-info |
| Rust | `rust/src/ui.rs` | ratatui UI、header、panel、debug overlay、help |
| Rust | `rust/src/i18n.rs` | 所有语言文案 + `Lang/t/set_lang/get_lang` |

另外已经新建过四个空目录：

```text
python/src/winload/i18n/
python/src/winload/ui/
rust/src/i18n/
rust/src/ui/
```

但当前还同时存在同名文件：

```text
python/src/winload/i18n.py
python/src/winload/ui.py
rust/src/i18n.rs
rust/src/ui.rs
```

这个状态不适合作为长期结构。

## 关键风险：同名文件 + 同名目录

Rust 里如果同时存在：

```text
rust/src/i18n.rs
rust/src/i18n/mod.rs
```

那么 `mod i18n;` 会遇到模块来源不唯一的问题。

Python 里如果同时存在：

```text
winload/i18n.py
winload/i18n/
```

也容易让 import 解析变得混乱，尤其后续加 `__init__.py` 后更明显。

所以如果决定目录化，应该是“迁移”，不是长期并存。

## 拆分原则

1. 对外 API 尽量不变。
2. Rust / Python 尽量保持概念对称。
3. 一次只拆一类职责，避免功能变更和结构调整混在一起。
4. `ui` 最容易出视觉和坐标问题，优先级不一定最高。
5. `i18n` 多数是数据搬迁，风险最低。
6. `main` 可以先拆出稳定边界，比如 `version`、`cli`、`debug`。

## 推荐路线 A：最稳路线

这个路线适合先降低风险。

### Step 1：先拆 i18n

Python：

```text
winload/i18n/__init__.py
winload/i18n/core.py
winload/i18n/en_us.py
winload/i18n/zh_cn.py
winload/i18n/zh_tw.py
```

Rust：

```text
rust/src/i18n/mod.rs
rust/src/i18n/en_us.rs
rust/src/i18n/zh_cn.rs
rust/src/i18n/zh_tw.rs
```

对外继续保持这些名字：

```text
t
set_lang
get_lang
Lang
```

这样调用方可以基本不变。

Python 调用方仍然写：

```python
from .i18n import t, set_lang, get_lang
```

Rust 调用方仍然写：

```rust
use i18n::{Lang, t, set_lang};
```

注意：迁移完成后要删除 `i18n.py` / `i18n.rs`，避免同名文件和目录并存。

### Step 2：再拆 main 的稳定职责

这一步目标不是把 `main` 变成 10 行，而是让它只管启动流程和 TUI loop。

Python：

```text
winload/cli.py        # argparse、parse_args、参数校验、参数类型转换
winload/debug.py      # --debug-info 输出
winload/version.py    # get_version、system info、build info version 文本
winload/main.py       # main、main_loop、curses 启动流程
```

Rust：

```text
rust/src/cli.rs       # Args、ValueEnum、parse_hex_color、parse_max_value、validate_args、help command
rust/src/debug.rs     # --debug-info 输出
rust/src/version.rs   # build info、system info、--version 输出
rust/src/main.rs      # main、App、DeviceView、run loop、terminal 启动流程
```

这个版本比 `runtime.py` / `app.rs` 更对称。

暂时不拆 `runtime.py`，因为 curses main loop 和入口启动流程强相关。

暂时不拆 `app.rs`，因为 Rust 的 `App` 状态和 run loop 现在放在 `main.rs` 里更直观。

如果以后 `App` 继续变大，再考虑 `app.rs`。

### Step 3：最后拆 ui

`ui` 最值得拆，但也最容易拆出小 bug。

Rust 可以考虑：

```text
rust/src/ui/mod.rs
rust/src/ui/header.rs
rust/src/ui/panels.rs
rust/src/ui/debug.rs
rust/src/ui/help.rs
rust/src/ui/text.rs
```

Python 可以考虑：

```text
winload/ui/__init__.py
winload/ui/core.py
winload/ui/header.py
winload/ui/panels.py
winload/ui/debug.py
winload/ui/help.py
winload/ui/text.py
```

建议职责：

| 模块 | 职责 |
|---|---|
| `core` / `mod` | 对外入口、`UI` 或 `draw` 主流程 |
| `header` | title、device header、loopback warning/info |
| `panels` | incoming/outgoing panel 绘制 |
| `debug` | F3 debug overlay |
| `help` | 底部 help bar |
| `text` | display width、padding、alignment、safe drawing helper |

迁移完成后要删除 `ui.py` / `ui.rs`，避免同名文件和目录并存。

## 推荐路线 B：先减 main 长度

如果短期最想降低 `main` 复杂度，可以先不碰 `i18n/ui` 目录。

顺序：

1. 拆 `version.py` / `version.rs`
2. 拆 `cli.py` / `cli.rs`
3. 拆 `debug.py` / `debug.rs`
4. 再回头拆 `i18n`
5. 最后拆 `ui`

优点：

- 直接降低入口文件长度。
- 刚加的 commit hash / commit time 逻辑天然适合进入 `version`。
- `debug-info` 逻辑独立，拆出去风险低。

缺点：

- 不能马上使用已经新建的 `i18n/` 和 `ui/` 空目录。
- 后续还要再处理同名文件/目录问题。

## 当前倾向

如果目标是最稳，选路线 A。

如果目标是先让 `main` 好看，选路线 B。

目前更倾向路线 A：

```text
i18n -> version -> cli -> debug -> ui
```

原因：

- `i18n` 是数据拆分，风险最低。
- `version/cli/debug` 都是边界清楚的逻辑。
- `ui` 最复杂，最后拆更安全。

## 拆分时的验收清单

每拆一步都至少检查：

```powershell
$env:PYTHONPATH='src'; python -m winload --version
$env:PYTHONPATH='src'; python -m winload --help
$env:PYTHONPATH='src'; python -m compileall src\winload
git diff --check
```

Rust 如果环境有 cargo：

```powershell
cargo check
cargo run -- --version
cargo run -- --help
```

UI 拆分后还需要人工跑一次 TUI：

```powershell
winload
winload -e
winload --debug-info
```

## 暂缓问题

- 是否真的需要把 `App` 从 Rust `main.rs` 拆出去。
- 是否需要 Python 也做 `app.py` 来强行对称。
- `ui/text.py` 和 Rust `ui/text.rs` 是否应该承担所有 display width 逻辑。
- `debug` 模块是否只管 `--debug-info`，还是也管 F3 overlay。
- `i18n` 文案是否后续改成 JSON/YAML，而不是代码常量。

## 结论

这次先只记录计划。

真正拆分时建议分多个小 commit。

不要在一个 commit 里同时做 i18n、ui、main 三类拆分。

每一步都保持外部命令和导入路径尽量不变。
